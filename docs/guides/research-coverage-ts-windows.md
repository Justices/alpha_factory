# Research coverage and TS window search

The default configuration enables `research.construction.coverage` and `ts_windows`.

```yaml
coverage:
  enabled: true
  stage_weights: [4, 2, 2]
ts_windows:
  enabled: true
  probe_windows: [5, 66, 252]
  candidate_windows: [5, 22, 66, 120, 252, 504]
  minimum_neighbor_ratio: 0.50
```

Coverage scheduling reconstructs selected-candidate counts from the root task catalog. It allocates ready capacity across exploration, optimization and terminal validation using the three weights, then favors less-tested datasets, fields and operator/structure groups. Empty phases lend capacity to available work. The weights are cumulative priorities, not rigid per-batch quotas. Each balanced feedback round contains at most eight candidates, and an exhausted task budget is not reset by restarting the coordinator. Reserved unique candidates consume the task budget even if their result later fails; platform retry attempts remain a separate bounded control.

The field loader now takes the configured field limit across datasets in round-robin order instead of filling it from the first large files. Coverage metrics therefore refer to this admitted field pool, not every field on the platform. A 500-field cap can still omit fields within a large dataset; increasing or rotating the admitted field pool is an explicit research decision.

Adaptive TS search currently applies to the **outer TS operator generated by raw-first-order**. Its initial grid is three probes. It groups feedback by source strategy, operator and canonical scalar input, so different fields and scalarizations never share a window winner. Only adjacent probes that both pass the exploratory parent gate and retain the configured Sharpe and Fitness ratios unlock intermediate windows from the finite candidate grid. Already cataloged or completed expressions are not regenerated. The outer range is not extrapolated: with the default probes, 504 is not automatically tested; include it in `probe_windows` when a long-horizon hypothesis warrants it.

This tests neighborhood sensitivity on existing backtest metrics. It does not estimate an optimal window from raw field autocorrelation, infer update frequency from field names, or establish cross-period/OOS stability. Explicit frequency metadata is preserved by field loading but does not automatically restrict windows in this version. Fixed windows inside preprocessing, database templates and AI-authored expressions remain unchanged.

To compare the previous scheduling or TS generation separately, set the corresponding `enabled` value to false in a separate experiment configuration. Preserve the same field snapshot, settings, seed and budget. Do not reinterpret an exhausted pool as exhaustive platform dataset coverage.

The 2026-09-07 live trial uses the production runtime/coordinator with an explicit two-field, four-operator probe strategy and terminal validation, at most 24 attempts. It uses its own SQLite database because the configured original database failed read-only schema access. This is a focused live experiment, not validation of every construction mode or a migration of existing production research state.
